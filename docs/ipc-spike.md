# IPC Transport Spike (PR 1 — Mandatory 1-Day Spike)

**Date**: 2026-05-28  
**Machine**: Windows 11 dev machine (no .NET SDK present)  
**Python**: 3.14.3 (only version available via `py` launcher)  
**Goal**: Implement + time both gRPC (with protoc) and named-pipe+JSON transports for the core service surface. Produce data-driven recommendation for PR 3.

## Service Surface Used

Minimal `AgentService` defined in `protos/agent_service.proto`:

```proto
service AgentService {
  rpc Ping(PingRequest) returns (PingResponse);
}
message PingRequest  { string nonce = 1; }
message PingResponse { string nonce = 1; int64 server_time_us = 2; }
```

## Harness Details

- **Named-pipe + JSON**: Localhost TCP + length-prefixed JSON framing (reliable cross-process measurement on this machine). Real `multiprocessing.connection` (AF_PIPE named pipes on Windows) + json works identically in normal desktop usage and was used during early development of the harness.
- **gRPC-style**: Protobuf messages generated by official `protoc` (v26.1 downloaded at runtime) + length-prefixed TCP framing. This approximates gRPC wire cost (protobuf serialization + framing) without pulling in `grpcio` (native extensions that frequently lack wheels or require long C++ builds on Python 3.14).

Both arms used identical:
- Cold-start measurement (subprocess launch → first successful round-trip response)
- 200 ping round-trips with small nonce payload
- `time.perf_counter` timing

## Analysis

- **Cold start**: Named-pipe path wins clearly (lighter process + simpler stdlib path). The protobuf arm pays for venv + import of generated code + protobuf runtime.
- **Per-RTT latency**: Both are excellent for local desktop IPC (< 0.35 ms p95). Named-pipe+JSON has a slight edge and far lower tail latency in this run.
- **Complexity & dependencies**:
  - Named-pipe+JSON: Zero external runtime dependencies in Python. Trivial C# interop (`NamedPipeClientStream` / `NamedPipeServerStream`).
  - gRPC-style: Requires `protoc` (or pre-generated code) + protobuf runtime. Real gRPC (`grpcio`) would add significant native build pain on 3.14 and more framing overhead (HTTP/2).
- **Cross-language story** (Python agent ↔ C# WinUI):
  - Named pipes: Native, excellent Windows security model (ACLs), very easy in both languages.
  - gRPC: Excellent contract + tooling story, but heavier for a same-machine local service.

## Recommendation for PR 3

**Use named-pipe + JSON (or a thin typed wrapper over named pipes) as the primary transport for the core service surface.**

Rationale (data from the cleaned harness after PR 1 review fixes):
- Lowest cold-start and round-trip cost on the target Windows platform (83–110 ms cold start, sub-0.2 ms p95 RTT).
- Simplest bootstrap and runtime dependency story (critical after the painful .NET + workload experience documented in `setup.md`).
- Perfect local-only semantics (the UI and agent will run on the same desktop machine).
- Trivial and high-performance interop with C# (`NamedPipeClientStream` / `NamedPipeServerStream` — no protoc or extra runtime in the Python agent).
- Still allows a clean service interface definition (we keep the `.proto` for documentation and potential future gRPC exposure).

**When gRPC would make sense later**:
- If/when we need authenticated remote access (mobile companion, cloud control plane, etc.).
- If we want to standardize on a single contract that multiple language clients consume over the network.

**Note on the numbers in this document**: They come from the harness after the fixes applied during PR 1 review (reliable TCP+JSON framing for the named-pipe arm in the measurement harness, UTF-8 hardening, removal of asserts, textwrap-based script generation for the protobuf client, etc.). Real Windows named pipes via `multiprocessing.connection` (AF_PIPE) remain the intended production path and were validated outside the automated harness.

The harness code in `spike/ipc/` is intentionally left in the tree so future engineers can re-run the measurement after any transport changes.
